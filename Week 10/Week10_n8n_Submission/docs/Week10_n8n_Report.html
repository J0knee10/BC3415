2. Setup

  • Route A (local), without Docker: n8n 2.44.6 installed with npm into a project folder, using a portable Node 24 (n8n 2.x needs Node ≥ 24; the machine's global Node 22 was left alone). Editor at http://localhost:5678, telemetry off, timezone Asia/Singapore.
  • Telegram: my own bot from @BotFather. The recipient is my numeric private chat id (from getUpdates after sending /start), not the bot's id, which avoids the guide's "bot can't send messages to the bot" 403 error.
  • Gemini: Google AI Studio key, stored as an n8n credential.
  • No secrets in this submission. Keys live only in n8n's encrypted credential store. The chat id is read at run time as {{ $env.TELEGRAM_CHAT_ID }}, so it isn't in any workflow JSON. Chat id, name and username are masked in screenshots and logs.
  • Reproducible: tools/n8n_setup.py rebuilds everything on a fresh n8n: Data Tables, seeded PO master, credentials (from environment variables), workflow import with id wiring, and publishing.

4. Customisation: V4 AP triage service

4.1 Business problem

Workflow C is a good teaching template, but the guide lists why it can't be used for real: the PO list is fixed in JavaScript, so finance can't update it; the duplicate check only knows one historic invoice, so the same invoice submitted twice is not caught ("Duplicate not detected on second submission"); it treats each invoice alone, so it misses patterns across invoices; every outcome sends the same Telegram message; and the Gemini note in D is never saved. These are exactly the gaps that let duplicate payments and approval-limit splitting through in real accounts-payable teams.

4.2 Design

WorkflowRole
sub | Core rules + AP ledgerLoads the PO master and the whole ledger from Data Tables, runs the V4 rules, writes each case to Week10_AP_Ledger_V4. Deterministic; no AI.
sub | Alerts + Gemini explanationSwitch by priority. P1 HOLD: instant Telegram, facts only. P2 REVIEW: Gemini explains, a guardrail checks it, the note is written back to the ledger row, then Telegram. P3 READY: no message (avoids alert fatigue).
E1 AP intake formForm for AP clerks; dropdown for the bank-change question; shows the triage result and case id when submitted.
E2 Batch invoice APIPOST /webhook/meridian-ap-v4/batch takes 1–200 invoices (e.g. from an OCR or email-capture system) and returns a JSON summary.
E3 Daily AP exception digestEvery weekday at 08:30 SGT: counts and amounts from the ledger; Gemini writes a 3-bullet briefing; a guardrail checks that every number in it exists in the data.

6. Problems met and how they were fixed

6.1 Gemini 503 (lab D, execution #7)

The template's models/gemini-3.8-flash answered "Service unavailable". A direct API check showed 3.8-flash and flash-latest overloaded, while gemini-flash-lite-latest answered normally. Following the guide's troubleshooting advice ("choose another currently accessible model"), workflow D now uses flash-lite with n8n's Retry on fail (3 tries, 5 s apart). Re-run #8: success.

6.2 Telegram "can't parse entities" (V4 alerts, first run)

The V4 alert text has status codes like HOLD_DUPLICATE, and Telegram read the underscores as Markdown. The lab template avoids this with parse_mode: None, which I had left out of my new Telegram nodes. Fixed, ledger reset, all scenarios re-run.

6.3 Other setup issues

  • n8n 2.x needs Node ≥ 24, so I used a portable Node 24 rather than changing the global install.
  • n8n 2.x will only publish a workflow if the sub-workflows it calls are published, so the setup script publishes sub-workflows first.

7. AI boundaries and reflection

Is this an agent? No. As the guide says, these are fixed workflows with a model in an advisory slot. In V4 the model writes text only; it cannot change a status, call a tool, approve or pay. Its output passes through code guardrails, tested in tests/test_guardrails.js against claims like "has been approved for payment", requests for bank details, a different status name, and invented numbers in the digest.

Two places where deterministic rules beat LLM judgement:

  1. Duplicate and re-billing detection. Whether supplier + reference already exists, or a PO is already used, is an exact lookup over every earlier invoice. Rules get it right every time and can be audited; a model reading invoices one at a time cannot see the history and could be talked out of it.
  2. Approval thresholds and split detection. "> $10,000" and "the sum this week > $10,000" are policy, not opinion. They must give the same answer on every run, and an auditor must be able to replay them. The model only explains why the rule fired.

Limitations:

  • Static fixtures (lab): V3's PO master and one-row history are constants in code, so they go stale and miss real duplicates. V4 moves both into Data Tables, but the PO table is still a manual copy, not a live ERP feed.
  • Guardrails check form, not meaning. In the digest, Gemini wrote "the 1 manager review case worth $54,050", but $54,050 is the total across four cases needing a manager. Each number exists in the data, so the guardrail passed it. The deterministic header above the AI text is the figure to rely on.
  • Split detection uses supplier name and a 7-day window; a real system would also match supplier ids, bank accounts and invoice dates.
  • The local n8n is not reachable from the internet (forms and the webhook work on this machine only), and the webhook has no authentication. Production would need HTTPS, header auth and a unique constraint on supplier + reference.
